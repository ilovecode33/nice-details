# Releasing

Versioning and changelogs in this monorepo are managed with
[Changesets](https://github.com/changesets/changesets). `@changesets/cli` 3.0.3 is a root
devDependency and the authoritative settings live in
[`.changeset/config.json`](.changeset/config.json). Every workspace — seven packages and three apps
— has a `CHANGELOG.md` in [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format (see
[`packages/ui/CHANGELOG.md`](packages/ui/CHANGELOG.md) for an example). Those files are generated by
Changesets and must not be hand-edited once changesets are in use.

## Configuration at a glance

- `baseBranch` is `main` and `access` is `restricted`.
- The `fixed` group ties `@ilovecode33/ui`, `@ilovecode33/ui-core`, `@ilovecode33/ui-tokens` and
  `@ilovecode33/ui-types` to the same version, so the UI family always upgrades as one unit.
- `updateInternalDependencies: "patch"` means that when a workspace dependency is bumped, its
  transitive internal dependents receive at least a patch bump in the same release.
- `privatePackages: { version: true, tag: false }` means private apps (`blog`, `editor-app`,
  `ui-landing`) and the `ai-rules` workspace are versioned and changelogged, but never published or
  tagged to npm.

## Commands

- `bun run changeset` — author a changeset interactively.
- `bun run version:packages` — consume all pending changesets: bump `package.json` versions, rewrite
  the `CHANGELOG.md` files and delete the consumed `.changeset/*.md` files.
- `bun run check:changesets` — run `changeset status --since=origin/main`; this must be green before
  a branch is merged. Changesets also considers uncommitted edits, so run it on a clean working
  tree.

## Workflow

1. For any user-visible or API change, run `bun run changeset`, select the affected workspaces and a
   bump type (`patch`, `minor` or `major`), and write a short summary. Commit the generated
   `.changeset/*.md` file together with the code change.
2. Before merging, run `bun run check:changesets` and make sure it is green.
3. Release time is automated: every push to `main` runs
   [`.github/workflows/release.yml`](.github/workflows/release.yml), which uses `changesets/action`
   to open or update the `chore: version packages` PR, validates the bumped workspace with
   typecheck/build/test, reports the required preview checks, and squash-merges it back to `main`.
   No manual `bun run version:packages` is needed. If the automation cannot merge (for example a
   failing check), the version PR stays open for manual review; merging it by hand is always safe.
4. Production deploys (`deploy-okr-web`, `deploy-blog`, `deploy-okr-realtime`) skip a push to `main`
   that still carries a releasable changeset, because it would ship new content under the previous
   version number. The version workflow dispatches all of them for the version commit, so content
   and version go live together. If the version PR cannot merge, merge it by hand (or run the deploy
   workflows manually with `workflow_dispatch`, which never skips). Every deploy workflow uses its
   own non-overlapping concurrency group, and they all call the shared
   [`pending-release`](.github/actions/pending-release/action.yml) action; new deploy workflows must
   do the same and be added to the dispatch loop in `release.yml`.

## Manual fallback

If the workflow is unavailable, run `bun run version:packages`, then `bun install` to refresh
`bun.lock`, verify with `bunx turbo run typecheck build test --force`, and commit the version and
changelog changes.

The summaries you write in changesets describe the change for readers, not the version number;
Changesets derives the version from the bump types.

## Dependent bumps

A patch-or-higher change to `@ilovecode33/ui-tokens` automatically bumps `ui-types`, `ui-core` and
`ui` (the fixed group keeps them aligned), and then the apps that depend on them. Likewise, a change
to `@ilovecode33/photo-wall` bumps `apps/ui-landing`. You do not need to list these transitive
dependents in the changeset yourself.
